# HomeRoad — 내집마련 프로젝트 플래너 설계서

> **한 줄 정의**: "언제 살 수 있나 / 못 사면 뭘 바꿔야 하나 / 이번 달엔 뭘 하나"를 계산으로 답하는 웹앱.
> 작성 기준일: 2026-08-02

---

## 0. 왜 기존 계산기와 다른가

시중에 널린 것들은 전부 **스냅샷**이다.
- 대출한도 계산기 → 지금 시점 한 숫자
- 청약가점 계산기 → 지금 시점 한 숫자
- 부동산 앱 → 지금 시세 한 숫자

내집마련은 스냅샷이 아니라 **3~5년짜리 프로젝트**다. 그래서 필요한 건 시간축이다.

핵심 질문 3개로 제품을 정의한다.

| # | 질문 | 담당 엔진 | 출력 |
|---|------|----------|------|
| Q1 | 지금 속도로 가면 **언제** 살 수 있나? | 교차점 솔버(E3) | 도달 예상 년월 or "미도달" |
| Q2 | 그때 못 사면 **뭘 바꿔야** 하나? | 레버 최적화(E4) | 레버별 민감도 순위 |
| Q3 | 그래서 **이번 달**에 뭘 하나? | 로드맵 생성기(E6) | 태스크 3~5개 |

**Q1이 이 제품의 심장이다.** 나머지는 다 부속이다.

### 교차점 솔버가 뭔가

두 곡선을 그린다.

```
필요자기자본(t) = 목표주택가격(t) - 최대대출(t) + 취득부대비용(t)     ← 집값 상승률 g로 증가
가용자기자본(t) = 현재순자산 × (1+i)^t + 월저축 × 연금종가계수(i,t)   ← 저축·수익률로 증가
```

두 곡선이 만나는 t가 **내집마련 가능 시점**.
만나지 않으면(집값 상승 속도 > 자산 증가 속도) → "현재 계획으로는 영원히 도달 불가" 라고 **정직하게** 말한다. 그 다음 레버 조정으로 넘어간다.

이 한 장의 그래프가 제품의 메인 화면이다.

### 2.2 절대 원칙 3개

**① 정책은 코드가 아니라 데이터다.**
LTV·DSR·특례대출 조건·특공 소득기준은 매년, 심하면 분기마다 바뀐다. 이걸 `if (region === '규제지역') ltv = 0.5` 처럼 하드코딩하면 6개월 뒤 죽은 앱이 된다. 전부 `policy/YYYY-MM.json`으로 뺀다. 각 항목에 `source_url`, `effective_date`, `verified_at`, `confidence`를 달고, `verified_at`이 90일 넘으면 UI에 **"⚠ 정책 검증 필요"** 배지를 띄운다.

**② 숫자는 엔진, 말은 LLM.**
LLM이 대출 한도를 계산하게 두면 그럴듯한 거짓말을 한다. 엔진이 계산한 숫자를 LLM에 **입력으로 주고 설명만 시킨다.** LLM 응답에 새 숫자가 등장하면 후처리에서 걸러낸다.

**③ 3-시나리오 강제.**
단일 예측은 거짓말이다. 보수(집값+4%, 수익률 2%, 금리 5%) / 기본 / 낙관 세 개를 항상 같이 보여준다. "2029년 3월 가능"이 아니라 "2028.11 ~ 2031.06, 중앙 2029.08".

### 2.3 배포 단계

| Phase | 형태 | 저장 | 기간 |
|-------|------|------|------|
| **P1 MVP** | 단일 HTML + JS (GitHub Pages) | localStorage + JSON export/import | 2~3주 |
| **P2** | React + Vite, 정책 JSON CDN 분리 | 동일 + 링크 공유(state를 URL 압축) | +2주 |
| **P3** | FastAPI + Postgres | 계정, 월간 이메일/알림, 실적 추적 | +4주 |

P1을 GitHub Pages 단일 파일로 뽑아두면 AI 재테크 연구소 사이트에 그대로 붙는다. 계정 없이 쓰다가 "저장하려면 가입" 으로 P3 유도.

## 3. 엔진 명세

### E1 — 자금여력 엔진 (`capacity`)

```
입력: profile, finance, target.priceNow, market.mortgageRate, policy
출력: { maxLoan, bindingConstraint, breakdown[], eligibleProducts[] }
```

**최대대출 = min(4개 제약)**

1. **LTV 제약** = 주택가격 × LTV비율
   - 규제지역/비규제지역/생애최초 여부로 분기 (정책 JSON)
2. **DSR 제약** — 실무상 이게 대부분 바인딩된다
   ```
   가용연간원리금 = 연소득 × DSR한도 − 기존부채 연간원리금
   스트레스금리   = 실행금리 + 스트레스가산금리          // 3단계 적용
   r = 스트레스금리 / 12,  n = 상환기간(월)
   최대대출 = 가용연간원리금 / 12 × [(1+r)^n − 1] / [r(1+r)^n]
   ```
3. **지역별 절대한도** — 수도권 규제지역 주담대 총액 캡 (가격구간별 차등)
4. **상품 한도** — 디딤돌/신생아특례/보금자리론 각 상품 자체 한도

`bindingConstraint`를 반드시 반환한다. "당신 한도를 막고 있는 건 LTV가 아니라 **신용대출 2천만원 때문에 깎인 DSR**입니다" — 이게 사용자가 진짜 알고 싶은 것이다.

**정책대출 자격 판정**은 별도 룰셋:
```
디딤돌 / 신생아 특례 디딤돌 / 보금자리론 / 청년주택드림
각각: 소득요건, 순자산요건, 주택가액요건, 면적요건, 무주택요건, 자녀요건
→ { product, eligible, failedRules[], hint }
```
`failedRules`가 핵심. "순자산 5.2억으로 기준 초과 → 잔금 전 4천만원 부채 상환 시 자격 회복" 같은 **행동 가능한 힌트**로 변환.

### E2 — 자산성장 엔진 (`growth`)

```
netWorth(t) = Σ asset_i × (1+r_i)^(t/12)
            + 월저축 × [(1+r_b)^t − 1] / r_b        // r_b = 월 환산 혼합수익률
            − 부채잔액(t)
            + 이벤트(t)                              // 전세금 회수, 상여, 증여 등
```

**이벤트 타임라인 필수**: 전세 만기(2027-05 → 1.8억 유입), 성과급, 차량 교체(−3천만), 결혼자금 증여. 내집마련은 큰 덩어리 현금 이벤트에 좌우된다. 매끈한 복리 곡선만 그리면 현실과 안 맞는다.

### E3 — 교차점 솔버 ★

```ts
function solveCrossover(state, scenario): CrossoverResult {
  for (let t = 0; t <= 240; t++) {          // 최대 20년, 월 단위 스캔
    const price   = target.priceNow * (1 + g) ** (t/12);
    const maxLoan = E1.capacity(state, price, t).maxLoan;
    const costs   = acquisitionCosts(price, state, policy);   // 취득세+중개보수+법무+이사+예비비
    const need    = price - maxLoan + costs;
    const have    = E2.netWorthLiquid(state, t);
    if (have >= need) return { reachable: true, month: t, price, need, have };
  }
  return {
    reachable: false,
    gapAt120: need(120) - have(120),
    divergence: d(need-have)/dt > 0        // 격차가 벌어지는 중인가
  };
}
```

**취득부대비용**도 정책 데이터로:
- 취득세 (가액구간별 세율, 생애최초 감면, 신생아 감면)
- 지방교육세 / 농특세
- 중개보수 (구간별 요율 상한)
- 법무사·등기 비용
- 이사·인테리어 예비비 (사용자 입력, 기본 주택가 3%)

이걸 빼먹은 계산기가 대부분이다. 5억 아파트면 부대비용 2~3천만원이 우습게 나온다.

**출력 UX**: 두 곡선 + 교차점 + 3시나리오 밴드. 미도달이면 곡선이 벌어지는 그림이 그대로 메시지가 된다.

### E4 — 레버 최적화

목표시점 달성이 안 될 때 조정 가능한 레버 6개. 각각의 **민감도**(1단위 변화 → 도달월 몇 개월 단축)를 계산해 순위를 매긴다.

| 레버 | 예시 조정 | 특징 |
|------|----------|------|
| L1 월저축 | +30만원 | 즉시 실행 가능, 효과 선형 |
| L2 목표가격 | 4.8억 → 4.2억 | 효과 가장 큼, 심리적 저항 큼 |
| L3 목표지역 | 유성구 → 서구 | L2의 현실적 구현 수단 |
| L4 기존부채 | 신용대출 2천 상환 | **DSR 한도 회복 → 대출 증가** 이중 효과 |
| L5 대출상품 | 일반 → 신생아특례 | 금리·한도 점프, 자격요건 충족 필요 |
| L6 목표시점 | 2029 → 2031 | 최후 수단, 집값 상승 리스크 증가 |

```
민감도(L) = [도달월(baseline) − 도달월(L + Δ)] / Δ
→ "월 30만원 더 모으면 7개월, 신용대출 상환하면 14개월 단축"
```

L4가 대체로 1위로 나온다. 대부분 이걸 모른다. 여기서 "아하" 가 나온다.

### E5 — 경로 적합도

5개 경로를 룰 기반 점수화 (LLM 아님, 결정론적).

| 경로 | 유리 조건 | 리스크 |
|------|----------|--------|
| **청약(민영)** | 가점 높음(무주택 오래+부양가족+통장 장기) | 당첨 불확실, 대기 장기화 |
| **특별공급** | 신혼7년내 / 생애최초 / 다자녀 / 신생아 / 노부모 | 소득·자산 상한 초과 시 탈락 |
| **공공분양·뉴홈** | 소득 낮고 자산 적음, 통장 납입회차 많음 | 지역·물량 제한 |
| **기존주택 매매** | 자금 충분, 시점 확실성 중요 | 시세 리스크 전액 부담 |
| **경매·공매** | 시간·지식 투입 가능, 현금 여유 | 명도·권리분석 리스크 |

점수 = Σ (조건 충족 × 가중치). 상위 2개를 **주경로/보조경로**로 제시하고, 청약은 "대기 중 매매 준비 병행"이 디폴트 전략.

청약 가점 계산은 별도 서브모듈:
```
가점 = 무주택기간(최대32) + 부양가족(최대35) + 통장가입기간(최대17) = 84점
```
※ 가점 배점 체계는 개편 논의가 진행 중 → 정책 JSON에서 배점표 자체를 데이터로 관리.

### E6 — 로드맵 생성기

**역산 스케줄링**: 목표일 D에서 거꾸로 마일스톤 배치 → 각 마일스톤의 게이트 조건 → 태스크 전개.

## 4. 로드맵 정의 (제품의 본체)

### 4.1 마일스톤 & 게이트

| ID | 마일스톤 | 게이트 통과 조건 (계산식) | 미통과 시 |
|----|---------|--------------------------|----------|
| M0 | 진단 완료 | 필수 입력 100%, 순자산 산출됨 | 온보딩 재개 |
| M1 | 목표 확정 | 목표지역+가격대+시점 확정, 교차점 계산됨 | L2/L3 조정 |
| M2 | 자금계획 확정 | `reachable == true` (기본 시나리오) | E4 레버 조정 루프 |
| M3 | 자격 정비 | 통장 요건 충족 && 정책대출 `failedRules == []` | 부채상환/자산조정 태스크 |
| M4 | 경로 확정 | 주경로 선택 && 보조경로 설정 | E5 재실행 |
| M5 | 시장 진입 | 가용현금 ≥ 계약금(10%) + 예비비 | 저축 가속 |
| M6 | 계약 체결 | 계약서 작성 + 계약금 납입 | — |
| M7 | 자금 조달 | 대출 승인액 ≥ 잔금 부족분 | **비상 플랜 발동** |
| M8 | 등기·입주 | 소유권이전등기 완료 | — |

## 5. AI 통합 — 시스템 프롬프트

### 원칙
1. LLM은 **숫자를 만들지 않는다.** 엔진 출력 JSON을 받아 설명만 한다.
2. 응답 후처리에서 숫자 추출 → 입력 JSON에 없는 숫자 발견 시 **차단 후 재생성**.
3. 정책 해석은 LLM에게 시키지 않는다. 정책 JSON이 진실이다.

### A1. 온보딩 자연어 파서

```
당신은 한국 주택 구입 상담의 데이터 추출기다.
사용자의 자유서술을 AppState 스키마 JSON으로 변환한다.

규칙:
- 명시되지 않은 값은 절대 추정하지 말고 null로 둔다.
- 추정 대신 missing_fields 배열에 필드명과 질문 문장을 담는다.
- 금액 단위를 정규화한다("3천5백만" → 35000000).
- 상대 표현은 기준일 {{TODAY}}로 절대일자화한다("작년 3월" → "2025-03").
- JSON만 출력. 설명·마크다운 코드펜스 금지.

출력 스키마: {{SCHEMA}}
사용자 입력: {{USER_TEXT}}
```

### A2. 결과 해설기

```
당신은 내집마련 계획 해설자다. 계산은 이미 끝났다.

절대 규칙:
- 아래 ENGINE_RESULT에 없는 숫자를 절대 쓰지 마라. 계산도 하지 마라.
- 금액/기간/비율을 새로 만들어내면 심각한 오류다.
- 확정적 미래 예측 금지. "~라면 ~로 계산됩니다" 형식만 사용.
- 특정 단지·지역 매수 권유 금지. 투자자문이 아니다.

구성 (한국어, 총 400자 내외):
1) 결론 한 문장 — 도달 가능 시점 또는 미도달 사실
2) 가장 큰 병목 하나 — bindingConstraint 기준
3) 효과 1순위 레버 하나 — 숫자와 함께
4) 이번 달 할 일 1개

ENGINE_RESULT:
{{RESULT_JSON}}
```

### A3. 월간 코칭

```
사용자의 지난달 실적과 계획을 비교해 짧은 코칭을 쓴다.

규칙:
- 200자 이내. 인사말·격려 상투구 금지.
- 미달성을 도덕적으로 비난하지 않는다. 숫자와 조정안만 제시.
- 3개월 연속 미달 시, 계획 자체의 재조정을 권한다(사용자 탓 아님).
- ENGINE_DELTA에 없는 숫자 사용 금지.

ENGINE_DELTA: {{DELTA_JSON}}
```

### A4. 공고문·매물 파서

```
입주자모집공고문 또는 매물 설명 텍스트에서 구조화 정보를 추출한다.

추출 필드: 공급유형, 공급세대수, 전용면적, 분양가, 계약금/중도금/잔금 비율과 일정,
청약자격(소득기준·자산기준·거주요건·통장요건), 당첨자발표일, 계약기간, 입주예정월

규칙:
- 원문에 없는 항목은 null. 일반 상식으로 채우지 마라.
- 각 필드마다 원문 근거 위치를 source_line에 남긴다.
- 애매한 표현은 ambiguous 배열에 원문 그대로 담고 확정하지 마라.
- JSON만 출력.

원문: {{DOCUMENT_TEXT}}
```

### A5. 리스크 감사

```
계약 직전 리스크 점검관 역할이다. 사용자의 계획 데이터를 보고
'놓치기 쉬운 실패 지점'만 지적한다. 잘한 점은 언급하지 마라.

점검 항목:
- 대출 미승인 시 계약금 회수 장치 유무
- 전세 만기일과 잔금일 정렬 여부
- 계약 후 잔금 전 근저당 신규 설정 확인 계획
- 취득 부대비용 반영 여부 (취득세·중개보수·법무·이사)
- 잔금 후 유동성 (비상금 6개월치 잔존 여부)
- 금리 상승 시 원리금 부담 (스트레스 시나리오)
- 정책 데이터 최신성 (verified_at 경과일)

각 항목: { risk, severity: high|med|low, action } 형태로 JSON 출력.
해당 없으면 항목 생략.

PLAN: {{PLAN_JSON}}
```

**P0 — 스캐폴딩**

- 생애최초/신생아 취득세 감면 반영
```

**P4 — E3 교차점 솔버 ★**
```
src/engines/e3_crossover.ts 구현. 이 프로젝트의 핵심이다.

solveCrossover(state, scenario): {
  reachable, monthIndex, targetYm,
  series: Array<{ month, price, maxLoan, needEquity, availEquity }>,
  gap, diverging
}

- 0~240개월 월단위 스캔
- 각 시점마다 집값 성장 → E1로 최대대출 재계산 → 부대비용 → 필요자기자본
- 가용자기자본은 E2의 유동자산 기준
- 미도달 시 diverging 판정 (격차의 1차 미분 부호)

runScenarios(state): 보수/기본/낙관 3종을 각각 실행해 밴드 반환
시나리오 파라미터는 policy가 아니라 별도 config로 분리.

테스트: 골든 케이스 5개 (도달/미도달/전세회수있음/정책대출적용/부채있음)
```

**P5 — E4 레버 최적화**
```
src/engines/e4_levers.ts:
- 레버 L1~L6 각각에 대해 Δ를 준 후 solveCrossover 재실행
- 민감도 = 도달월 단축 개월수 / Δ단위
- 결과를 효과 순으로 정렬해 반환
- L4(기존부채 상환)는 DSR 회복 효과가 함께 계산되는지 반드시 검증

성능: 6레버 × 3시나리오 × 240개월 스캔 → 웹워커로 분리하거나
E1을 메모이제이션. 300ms 이내 목표.
```

**P6 — E5 경로 + E6 로드맵**
```
src/engines/e5_route.ts:
- 5개 경로 룰 기반 스코어링, 청약가점 계산 서브모듈 포함
- 배점표는 policy에서 로드

src/engines/e6_roadmap.ts:

**P7 — 오케스트레이션 + UI**

UI 5개 화면:

   각 스텝 이탈해도 진행 저장. 스킵 가능 필드 명확히 표시.

3. 레버: 슬라이더 6개, 조작 시 실시간 재계산, 효과 순위 표시
4. 로드맵: 세로 타임라인, 마일스톤 게이트 pass/fail 뱃지, 태스크 체크박스
5. 실적: 월별 계획 vs 실제 입력, 달성률 추이

localStorage 저장 + JSON export/import.

**P8 — AI 어댑터**
```
src/ai/ 구현:
- prompts.ts: A1~A5 프롬프트 템플릿
- client.ts: Anthropic API 호출 래퍼, 재시도, 타임아웃
- guard.ts ★: 응답에서 숫자 토큰 추출 → 입력 JSON에 존재하지 않는
  숫자가 있으면 재생성 요청(최대 2회), 그래도 실패하면 AI 해설 없이

```

## 9. 리스크 & 고지

**필수 면책 문구** (하단 상시 노출)
> 본 서비스는 공개된 제도 정보를 바탕으로 한 계산 도구이며 투자자문·금융자문·세무자문이 아닙니다. 대출 한도와 금리, 청약 자격, 세액은 금융기관 심사와 관계기관 판단에 따라 달라집니다. 실제 계약 전 반드시 해당 금융기관·청약홈·세무 전문가를 통해 확인하시기 바랍니다.

**주요 리스크**
| 리스크 | 대응 |
|--------|------|
| 정책 수시 변경 | 정책 데이터 분리 + verifiedAt 만료 경고 + 분기 검증 루틴 |
| 사용자가 예측을 확정으로 오해 | 3-시나리오 밴드 강제, 단일 숫자 노출 금지 |
| LLM 환각 숫자 | guard.ts 숫자 검증, 실패 시 AI 해설 미표시 |
| 개인 금융정보 | P1~P2는 서버 전송 0, 전부 로컬. P3 도입 시 암호화·최소수집 |
| 특정 매물 추천으로 오인 | 지역·가격대 단위까지만. 개별 단지 매수 권유 금지 |
